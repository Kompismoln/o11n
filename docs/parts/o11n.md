# o11n

The `o11n` command reads an org's export, as `org.export` of its flake evaluates it or `O11N_EXPORT` names it, and acts
on the org.

## Status

`o11n status [group]...` (`crates/o11n/src/status.rs`) checks each entity of the groups, all of them by default, by what
the org's export says it has, and prints a line a check: `<id> <check> ok`, `fail: <why>` or `skip: <why>`, in the order
planned, as soon as those before it are done. It fails when a check does, not when one is skipped. `--list` prints the
checks without running them, and `--failed` only those that fail. It changes nothing: no mail is sent, no key written.

An entity's checks run one after another, and the entities side by side. Over ssh, o11n knows a host by the ssh-key the
org has the public key of and no other, and shares a connection to each user at each host for the run
(`crates/o11n/src/ssh.rs`), unless the temporary directory's path leaves no room for its sockets. A host spares the
org's own addresses, `<prefix>::/48` and `<prefix4>.0.0/16`, sshd's `PerSourcePenalties`, which would refuse them for
connections that don't log in (`nixos/org/ssh.nix`).

### Checks

An entity needs an identity for secrets: of its own, beyond its age-key, or another's it decrypts, as one of its grants
or actors. One that needs none, as a store or service whose sops file would hold nothing, has none of the checks of its
identity, sops file and keys until it has an identity anyway.

Without a secret, from the org's clone:

- `identity`: an entity but a root has its identity file.
- `recipients`: its sops file is encrypted to the age keys `o11n sops-yaml` gives it, and to no other.
- `public-key <key>`: each of its keys with a public key in a file has it.

With a secret, each skipped when the operator can't decrypt it:

- `secret <key>`: each of its keys is in its sops file or identity, and its public key is the one it derives, as
  `o11n public-key verify` has it; a key with slots, as a luks-key, is each slot the org holds, as it should be.
- `secrets`: its sops file holds nothing but its keys, a key's slots and a password's hash.
  `o11n secret extra [group]...` lists what else it holds, as `<id> <path>`, the path from the file's top. A secret the
  org's own configuration reads, as a host's `wifi-keys`, is declared under the entity's `keys` as a `file`, taken as
  it's given (`o11n secret generate <id> <key> --from <file>`), with no public key; the rest is taken out with
  `o11n secret edit`.

On a host with NixOS, over ssh, each skipped for a host without an `endpoint` that doesn't answer, as a workstation
that's off, and failed for one with:

- `ssh-key`: the host answers with the ssh-key of its public key, which `o11n host pull-ssh-key` writes: a host's
  ssh-key is its own, and the org has no secret of it. It does so on the connection that logs in as `locksmith`, or else
  `nix-switch`, which the host's other checks share, or, without either or a shared connection, to `ssh-keyscan`.
- `on-host age-key`, `on-host luks-key`: on a host with the `locksmith` service, the host has its identity and each slot
  of its luks-key the org holds, as `o11n host check` has it, with service-locksmith's ssh-key.
- `initrd-key`: on such a host with a luks-key, the initrd the system profile boots, where its boot loader wrote it,
  holds a luks-key that opens the host's disk, and it's the org's slot 0, which a deployment writes, unless the org has
  no slot 0 (`nixos/services/locksmith.sh`).
- `version`: on a host with the `nix-switch` service, the system it runs was built from the org's tree as it is where
  o11n runs, uncommitted changes included, and from the o11n the org's `flake.lock` pins, by the narHash of each, which
  `switch-system status` tells of the trees the host keeps at `/etc/nix/inputs/self` and `/etc/nix/inputs/o11n`
  (`nixos/org/nix.nix`), with service-nix-switch's identity (`crates/o11n/src/version.rs`). A host that runs a system
  from before it kept them is skipped.
- `reboot`: on such a host, the system it boots next has the kernel and kernel modules it runs.
- `allotment-sync <id> <replica>` and `allotment-conflicts <id>`: on such a host, each allotment with replicas syncs
  with each, and holds no conflicting copy (`docs/parts/allotments.md`).

Of the org, before the entities':

- `org o11n`: the o11n that runs is the package the o11n the org's `flake.lock` pins builds, whatever else differs in
  their trees; skipped for an o11n outside the nix store, as one cargo built.

From outside, against what the org declares:

- `url <url>`: an app's `url` answers with a certificate curl trusts and a status below 500.
- `nix-daemon`: a host with the `nix-remote` or `remote-builder-relay` service answers `/nix-daemon/probe` on its
  endpoint with 401, as nix-remote's nginx refuses a request without the bearer, or 404, through a proxy that adds it.
- `nix-store`: the store answers `nix store info` through the tunnel `o11n remote` opens, with nix-remote's
  `secret-key`, or else `O11N_REMOTE_BUILDER_TOKEN`, or no bearer for the builder `O11N_REMOTE_BUILDER` names.
- `submission mail.<endpoint>`: on the host with the `mailserver` service, submission on 587 takes STARTTLS with a
  certificate curl trusts, and NOOP.
- `mail-login mail.<endpoint>`: a principal with a `mail` key logs in to submission as its `mail.address`, and says
  NOOP.

From the internet's DNS, as a receiver reads it, over https from `O11N_DOH`, Cloudflare's by default
(`crates/o11n/src/dns.rs`):

- `mx <domain>`: on the host with the `mailserver` service, a domain with `mailbox` has `mail.<endpoint>` among its MX.
- `spf <domain>`, `dkim <domain>` and `dmarc <domain>`: on the host with the `mailserver` service for a domain a
  principal that sends has its address on, and on a principal that sends for a domain of its `sendAs` that isn't one of
  those. Its SPF passes each address of `mail.<endpoint>`, as RFC 7208 evaluates it but for `exists` and `ptr`, which
  match nothing; `<dkimSelector>._domainkey.<domain>` has one DKIM key; and `_dmarc.<domain>` has one DMARC record with
  a policy.

### The export

For these, `org.export` has a host's `services`, by name, an app's `url`, a principal's `mail` (`address`, `inbox`,
`send`, `sendAs`) when it has an inbox or sends, and `mailserver`'s `endpoint`, `dkimSelector` and `domains`, each with
its `mailbox` and whether it's `sent` from, a principal's address on it, or `mailserver` null.

### Work in progress

- `mail-login` tries the login from where o11n runs, not from the principal's host with its own client, so it says
  nothing of an app's mailer, as mobilizon's was when its TLS options left out the CA certificates.
- A `url` that redirects is taken as it answers, without following it.
- `dkim` finds a key, not that it's the one the server signs with, which only the server has.
- `spf` takes the server to send from the addresses of `mail.<endpoint>`, which a host with another outbound address
  doesn't.
- Nothing tests `nix-store` but by hand, and no check asks the builder to build.
